## 一、项目背景与目标

本项目（KanoProject）已集成 LangChain4j 1.0.0-alpha1 与 Milvus 向量数据库。本模块在已有 AI 对话能力之上实现**文档知识库**与 **RAG 问答**：

- **文档知识库**：外部提交 txt / pdf / doc / docx 等文档，系统解析文本 → 切分 → 向量化 → 写入 Milvus，并提供相似度检索与按文档删除能力。
- **RAG 问答**：用户提问时先从向量库检索相关资料，把资料注入大模型提示词，得到「有依据」的回答。

**设计目标：**

| 目标 | 落点 |
|---|---|
| 强复用性 | 解析 / 切分 / 存储 / 入库管线四个维度全部接口化，实现可替换 |
| 零 DDL 运维 | 集合由 MilvusEmbeddingStore 首次写入时自动创建 |
| 多知识库隔离 | collectionName 参数化，一套代码支撑 N 个集合 |
| 贴合现有分层 | 编排逻辑在 dao 层，dubboImpl 只做薄转发 |

### 2.2 文档上传数据流

```text
外部（Dubbo RPC） uploadDocument(DocumentIngestDTO)
  ▼
DocumentServiceImpl                薄转发，异常捕获转 Result.fail
  ▼
DocumentDaoImpl.upload()
  ① SupportedFileTypes.isSupported()      校验扩展名白名单
  ② UUID.randomUUID()                     生成 documentId
  ③ DocumentParser.parse()                Tika 抽取纯文本
  ④ DocumentIngestor.ingest()
       ├─ DocumentSplitter.split()         切分 + 合并元数据 + 追加 chunkIndex
       ├─ EmbeddingModel.embedAll()        批量向量化（qwen，维度读配置）
       └─ EmbeddingStore.addAll()          写入 Milvus（集合不存在自动创建）
  ⑤ 返回 DocumentResultVO(documentId, fileName, collectionName, chunkCount)
```

### 2.3 RAG 问答数据流

```text
外部（Dubbo RPC） doChatWithRag(memoryId, message, collectionName, topK)
  ▼
AiServiceImpl                    薄转发
  ▼
AiChatDaoImpl.doChatWithRag()
  ① DocumentDao.search()         向量检索 topK 个相关分块
  ② buildRagPrompt()             把分块拼成 system 提示词（约束只依据资料回答）
  ③ 取 Redis 历史                memoryStore.getMessages(memoryId)
  ④ chatModel.generate()         消息顺序：[system + 历史 + 当前问题]
  ⑤ 回写记忆                     [历史 + 本轮 user + ai]
```

## 三、依赖与 LangChain4j 关键 API 说明

### 3.1 新增依赖

```xml
dev.langchain4j:langchain4j-document-parser-apache-tika   # 文本解析（txt/pdf/doc/docx 全支持）
dev.langchain4j:langchain4j-embeddings                    # 向量化
dev.langchain4j:langchain4j-milvus                        # Milvus 向量存储
```

### 3.2 版本冲突修复（重要）

Tika 3.0 对两个库有最低版本要求，但项目里被旧依赖覆盖，运行时报错。已在 provider 模块 pom **显式声明直接依赖**（直接依赖深度 1 压过传递依赖深度 2）：

| 冲突 | 旧版本（谁带入） | 修复版本 | 原因 |
|---|---|---|---|
| commons-io | 2.11.0（easyexcel-core） | **2.16.1** | Tika 3.0 需要 `UnsynchronizedByteArrayInputStream.builder()`（2.16 新增） |
| gson | 2.8.6（kano-project-common） | **2.10.1** | Tika 3.0 需要 `ToNumberStrategy`（2.8.9 新增） |

两个都是 2.x 向后兼容升级，不影响原有功能。

### 3.3 该版本的几个「反直觉」API（写代码前务必用 javap 核对）

| API | 注意点 |
|---|---|
| `DocumentSplitter` 接口 | 在 `dev.langchain4j.data.document.DocumentSplitter`（**不在** `.splitter` 子包）；`DocumentByParagraphSplitter` 等具体实现才在 `.splitter` 下 |
| `ApacheTikaDocumentParser` | 完整包名是 `dev.langchain4j.data.document.parser.apache.tika.ApacheTikaDocumentParser`（多一层 `apache.tika`） |
| `MilvusEmbeddingStore.builder()` | **没有** `createCollection` 参数，首次 `add` 时内部自动建集合，无需手工 DDL |
| 元数据存储 | 以 JSON 字段落库；`removeAll(Filter)` 经 `MilvusMetadataFilterMapper` 映射成 JSON 路径表达式，按 documentId 过滤删除可用 |
| `EmbeddingStoreIngestor.IngestionResult` | **没有** `ids()`，拿不到分块数；需要时改用手动三步：`split → embedAll → store.addAll()`（默认 addAll 会生成 id 并返回 `List<String>`） |
| `Metadata` | `put(String,String)` 可用且不过时；`asMap()` / `add(String,Object)` 已过时，统一用 `toMap()` + `put()` |

## 五、核心代码详解

### 5.1 api 模块（对外契约）

#### 5.1.1 service/DocumentService.java

职责：文档知识库对外能力契约，消费方只依赖本接口。

```java
public interface DocumentService {
    Result<DocumentResultVO> uploadDocument(DocumentIngestDTO dto);           // 单文档入库
    Result<List<DocumentResultVO>> uploadBatch(List<DocumentIngestDTO> dtos); // 批量入库
    Result<Boolean> deleteDocument(String documentId, String collectionName); // 按文档删除向量
    Result<List<DocumentChunkVO>> search(DocumentSearchDTO dto);              // 相似度检索
    Result<Boolean> deleteCollection(String collectionName);                  // 删除整个集合
}
```

- `Result<T>` 是公共返回体，`success` / `fail` 静态工厂。
- `collectionName` 做成可空参数：为空走默认知识库，传入即指定集合。

#### 5.1.2 四个 DTO

| DTO | 关键字段 | 用途 |
|---|---|---|
| `DocumentIngestDTO` | fileName / fileContent(byte[]) / collectionName / metadata | 入库入参，Dubbo 传二进制 |
| `DocumentResultVO` | documentId / fileName / collectionName / chunkCount | 入库结果 |
| `DocumentSearchDTO` | query / topK / minScore / collectionName | 检索入参 |
| `DocumentChunkVO` | documentId / fileName / chunkIndex / text / score | 检索命中分块 |

### 5.2 document 包（可复用组件）

> 设计思想：把「文件解析 / 文本切分 / 向量存储 / 入库管线」拆成四个正交接口，任何一层更换实现（换 OCR、换切分算法、换向量库）都不影响其他层与上层编排。

#### 5.2.1 DocumentMetadataKeys.java

统一管理写入 Milvus 的分块元数据 Key，避免字符串散落拼错导致过滤失效：

```java
public final class DocumentMetadataKeys {
    public static final String DOCUMENT_ID = "documentId";  // 文档唯一标识
    public static final String FILE_NAME   = "fileName";    // 文件名
    public static final String CHUNK_INDEX = "chunkIndex";  // 分块序号
}
```

#### 5.2.2 SupportedFileTypes.java

入库前校验扩展名白名单，白名单外直接拒绝。底层由 Tika 统一解析，新增格式只加一个扩展名：

```java
private static final Set<String> SUPPORTED = new HashSet<>(Arrays.asList(
        "txt", "pdf", "doc", "docx", "md", "html", "xml", "rtf", "csv"));
```

#### 5.2.3 DocumentParser.java + impl/TikaDocumentParser.java

```java
public interface DocumentParser {
    String parse(byte[] fileBytes, String fileName);   // 从文件二进制抽取纯文本
}

@Component
public class TikaDocumentParser implements DocumentParser {
    private final ApacheTikaDocumentParser delegate = new ApacheTikaDocumentParser();
    @Override
    public String parse(byte[] fileBytes, String fileName) {
        Document document = delegate.parse(new ByteArrayInputStream(fileBytes));
        return document.text();
    }
}
```

一个实现覆盖所有常见格式，是「零改动扩展格式」的关键；抽象接口让上层不依赖具体解析库。

#### 5.2.4 DocumentSplitter.java + impl/ConfigurableDocumentSplitter.java（核心）

把 LangChain4j 四种 splitter 封装成可配置策略，策略与粒度全部走 `application.properties`：

```java
@Component
public class ConfigurableDocumentSplitter implements DocumentSplitter {
    private final dev.langchain4j.data.document.DocumentSplitter delegate;   // 全限定名区分同名接口

    public ConfigurableDocumentSplitter(
            @Value("${doc.splitter.type:paragraph}") String type,
            @Value("${doc.chunk.size:500}") int chunkSize,
            @Value("${doc.chunk.overlap:50}") int chunkOverlap) {
        this.delegate = buildDelegate(type, chunkSize, chunkOverlap);
    }

    private static dev.langchain4j.data.document.DocumentSplitter buildDelegate(...) {
        switch (type.toLowerCase()) {
            case "character": return new DocumentByCharacterSplitter(chunkSize, chunkOverlap);
            case "sentence":  return new DocumentBySentenceSplitter(chunkSize, chunkOverlap);
            case "recursive": return DocumentSplitters.recursive(chunkSize, chunkOverlap);
            case "paragraph":
            default:          return new DocumentByParagraphSplitter(chunkSize, chunkOverlap);
        }
    }

    @Override
    public List<TextSegment> split(String text, Metadata baseMetadata) {
        List<TextSegment> rawSegments = delegate.split(new Document(text, baseMetadata));
        List<TextSegment> result = new ArrayList<>(rawSegments.size());
        for (int i = 0; i < rawSegments.size(); i++) {
            Metadata segmentMetadata = new Metadata();
            if (baseMetadata != null) {
                for (Map.Entry<String, Object> entry : baseMetadata.toMap().entrySet()) {
                    segmentMetadata.put(entry.getKey(), String.valueOf(entry.getValue()));
                }
            }
            segmentMetadata.put(DocumentMetadataKeys.CHUNK_INDEX, String.valueOf(i));  // 追加分块序号
            result.add(TextSegment.from(rawSegments.get(i).text(), segmentMetadata));
        }
        return result;
    }
}
```

**关键点：** 切分后手动重建每个分块的 `Metadata` —— 把基础元数据（documentId/fileName/业务标签）合并进去并追加 `chunkIndex`。这是「按文档删除」「溯源」「排序」的基础。

#### 5.2.5 VectorStoreManager.java + impl/MilvusVectorStoreManager.java（核心）

按集合名懒加载并缓存 `MilvusEmbeddingStore`，一套代码支撑多知识库：

```java
@Component
public class MilvusVectorStoreManager implements VectorStoreManager {
    private final Map<String, EmbeddingStore<TextSegment>> storeCache = new ConcurrentHashMap<>();

    @Override
    public EmbeddingStore<TextSegment> getStore(String collectionName) {
        String collection = resolveCollection(collectionName);
        return storeCache.computeIfAbsent(collection, this::createStore);   // 并发下每集合只建一个实例
    }

    private MilvusEmbeddingStore createStore(String collectionName) {
        return MilvusEmbeddingStore.builder()
                .uri(uri).token(token).databaseName(databaseName)
                .collectionName(collectionName)
                .dimension(dimension)                 // 动态读 ${embedding.model.dimensions}
                .metricType(MetricType.COSINE)        // 余弦相似度
                .build();
    }
}
```

#### 5.2.6 DocumentIngestor.java + impl/LangChain4jIngestor.java（核心）

把切分、批量向量化、批量写入串成一条标准管线，复用项目已有 `EmbeddingModel` Bean：

```java
@Component
public class LangChain4jIngestor implements DocumentIngestor {
    private final DocumentSplitter documentSplitter;
    private final EmbeddingModel embeddingModel;      // 复用 AiProjectConfig 的 qwen 向量模型 Bean
    private final VectorStoreManager vectorStoreManager;

    @Override
    public List<String> ingest(String text, String collectionName, Map<String, String> metadata) {
        Metadata baseMetadata = new Metadata();
        if (metadata != null) metadata.forEach(baseMetadata::put);

        List<TextSegment> segments = documentSplitter.split(text, baseMetadata);
        if (segments.isEmpty()) return List.of();

        Response<List<Embedding>> embedResponse = embeddingModel.embedAll(segments); // 批量向量化
        EmbeddingStore<TextSegment> store = vectorStoreManager.getStore(collectionName);
        return store.addAll(embedResponse.content(), segments);                       // 批量写入并返回 id
    }
}
```

> **为什么不用 `EmbeddingStoreIngestor`**：该版本 `IngestionResult` 没有 `ids()`，拿不到分块数；改用手动三步同样走标准流程，还能返回每个分块 id。`store.addAll(embeddings, segments)` 默认实现会 `generateIds` 再调用 MilvusEmbeddingStore 覆写的三参 `addAll` 真正落库。

### 5.3 dao 层（业务编排）

#### 5.3.1 DocumentDao.java + DocumentDaoImpl.java（重点）

`DocumentDaoImpl` 是文档编排核心，构造器注入四个可复用组件，职责单一、可测试：

```java
@Service
public class DocumentDaoImpl implements DocumentDao {
    private final DocumentParser documentParser;
    private final DocumentIngestor documentIngestor;
    private final VectorStoreManager vectorStoreManager;
    private final EmbeddingModel embeddingModel;

    // ---------- 入库 ----------
    public DocumentResultVO upload(DocumentIngestDTO dto) {
        validate(dto);                                       // ① 校验文件类型/内容非空
        String documentId = UUID.randomUUID().toString();    // ② 生成文档 ID
        String text = documentParser.parse(dto.getFileContent(), dto.getFileName()); // ③ 解析
        if (!StringUtils.hasText(text)) {
            throw new IllegalArgumentException("文档内容解析为空，请检查文件格式: " + dto.getFileName());
        }
        Map<String, String> metadata = new LinkedHashMap<>();
        metadata.put(DocumentMetadataKeys.DOCUMENT_ID, documentId);
        metadata.put(DocumentMetadataKeys.FILE_NAME, dto.getFileName());
        if (dto.getMetadata() != null) metadata.putAll(dto.getMetadata());   // 合并业务元数据
        String collectionName = vectorStoreManager.resolveCollection(dto.getCollectionName());
        List<String> chunkIds = documentIngestor.ingest(text, collectionName, metadata); // ④ 入库
        return new DocumentResultVO(documentId, dto.getFileName(), collectionName, chunkIds.size());
    }

    // ---------- 按 documentId 删除 ----------
    public boolean delete(String documentId, String collectionName) {
        EmbeddingStore<TextSegment> store = vectorStoreManager.getStore(collectionName);
        Filter filter = MetadataFilterBuilder.metadataKey(DocumentMetadataKeys.DOCUMENT_ID)
                .isEqualTo(documentId);                       // 构造 documentId == "xxx"
        try {
            store.removeAll(filter);                          // 映射成 JSON 路径表达式删除
            return true;
        } catch (Exception e) {
            log.warn("文档删除失败 documentId={}", documentId, e);
            return false;                                     // 集合不存在等场景不抛异常
        }
    }

    // ---------- 相似度检索 ----------
    public List<DocumentChunkVO> search(DocumentSearchDTO dto) {
        EmbeddingStore<TextSegment> store = vectorStoreManager.getStore(dto.getCollectionName());
        Embedding queryEmbedding = embeddingModel.embed(dto.getQuery()).content(); // 问题向量化
        EmbeddingSearchRequest request = EmbeddingSearchRequest.builder()
                .queryEmbedding(queryEmbedding)
                .maxResults(dto.getTopK() == null ? defaultTopK : dto.getTopK()) // 默认读 doc.search.topk
                .minScore(dto.getMinScore() == null ? 0.0 : dto.getMinScore())
                .build();
        List<EmbeddingMatch<TextSegment>> matches = store.search(request).matches();
        // 逐条把分块元数据还原成 VO：documentId/fileName/chunkIndex/text/score
    }
}
```

**三个关键链路：**
- **删除**：元数据存了 documentId → `Filter` → `removeAll(Filter)`，不需要手动查 id 再删。
- **检索**：query 用同一个 `EmbeddingModel` 编码，保证向量空间一致。
- **校验**：文件内容非空 + 扩展名白名单，不合法抛异常由 dubbo 层包装成 `Result.fail`。

#### 5.3.2 AiChatDaoImpl.doChat（原有聊天逻辑，RAG 复用其记忆机制）

```java
@Override
public String doChat(Long memoryId, UserMessage message) {
    List<ChatMessage> messageList = new ArrayList<>();
    messageList.add(message);
    List<ChatMessage> historyMessage = memoryStore.getMessages(memoryId);   // 取历史
    if (!historyMessage.isEmpty()) messageList.addAll(historyMessage);
    Response<AiMessage> res = chatModel.generate(messageList);               // 生成
    messageList.add(res.content());
    memoryStore.updateMessages(memoryId, messageList);                       // 回写记忆
    return res.content().text();
}
```

### 5.4 dubbo 层（薄转发）

`DocumentServiceImpl` 与 `AiServiceImpl` 都只做两件事：**转发给 dao 编排层 + 捕获异常转 `Result.fail`**，避免异常穿透 RPC：

```java
@Service   // org.apache.dubbo.config.annotation.Service，暴露为 Dubbo 服务
public class DocumentServiceImpl implements DocumentService {
    @Autowired
    private DocumentDao documentDao;

    @Override
    public Result<DocumentResultVO> uploadDocument(DocumentIngestDTO dto) {
        try {
            return Result.success(documentDao.upload(dto));
        } catch (Exception e) {
            log.warn("文档入库失败 fileName={}", dto == null ? null : dto.getFileName(), e);
            return Result.fail(e.getMessage());
        }
    }
}
```

## 六、RAG 接入详解

### 6.1 思路

RAG（检索增强生成）= **先检索资料，再基于资料生成回答**。完全复用已有能力：
- 检索 → 复用 `DocumentDao.search()`
- 生成 → 复用 `chatModel` + Redis 记忆

### 6.2 接口与编排

api 层 `AiService` 新增方法，`AiServiceImpl` 薄转发到 `AiChatDao.doChatWithRag`。

```java
// AiService.java
Result<String> doChatWithRag(Long memoryId, String message, String collectionName, Integer topK);
```

### 6.3 核心实现（AiChatDaoImpl）

```java
@Override
public String doChatWithRag(Long memoryId, String message, String collectionName, Integer topK) {
    // 1. 向量检索相关资料
    DocumentSearchDTO searchDTO = new DocumentSearchDTO();
    searchDTO.setQuery(message);
    searchDTO.setCollectionName(collectionName);
    searchDTO.setTopK(topK == null ? defaultTopK : topK);   // 默认读 doc.search.topk
    List<DocumentChunkVO> chunks = documentDao.search(searchDTO);

    // 2. 用检索到的资料组装 system 提示词
    String systemPrompt = buildRagPrompt(chunks);

    // 3. 按时间顺序组装消息：system + 历史 + 当前问题
    List<ChatMessage> history = memoryStore.getMessages(memoryId);
    List<ChatMessage> generateList = new ArrayList<>();
    generateList.add(SystemMessage.from(systemPrompt));
    generateList.addAll(history);
    generateList.add(UserMessage.from(message));

    // 4. 生成回答
    Response<AiMessage> res = chatModel.generate(generateList);

    // 5. 持久化本轮 user + ai；system 提示词每轮随检索结果变化，不入历史库
    List<ChatMessage> persisted = new ArrayList<>(history);
    persisted.add(UserMessage.from(message));
    persisted.add(res.content());
    memoryStore.updateMessages(memoryId, persisted);

    return res.content().text();
}

private String buildRagPrompt(List<DocumentChunkVO> chunks) {
    if (chunks == null || chunks.isEmpty()) {
        return "你是一个知识库问答助手。资料库中未检索到相关内容，请直接告诉用户“未检索到相关资料”，不要编造。";
    }
    StringBuilder context = new StringBuilder();
    for (DocumentChunkVO chunk : chunks) {
        int index = chunk.getChunkIndex() == null ? 0 : chunk.getChunkIndex() + 1;
        context.append("【资料】").append(chunk.getFileName())
                .append("（第").append(index).append("段，相似度 ")
                .append(String.format("%.2f", chunk.getScore())).append("）：\n")
                .append(chunk.getText()).append("\n\n");
    }
    return loadRagSystemPrompt() + "\n\n"          // system 模板从 .txt 文件读取
            + "==================== 检索到的资料 ====================\n"
            + context
            + "====================================================\n";
}

/**
 * 从配置的 .txt 文件读取 RAG system 提示词模板（rag.system.prompt.path）；
 * 默认 classpath:prompts/RagSystemPrompt.txt，支持 file:绝对路径；读取失败回退内置默认
 */
private String loadRagSystemPrompt() {
    try (InputStream in = ragSystemPromptResource.getInputStream()) {
        return new String(in.readAllBytes(), StandardCharsets.UTF_8).trim();
    } catch (IOException e) {
        log.warn("读取 RAG system 提示词失败: {}", ragSystemPromptResource, e);
        return "你是一个知识库问答助手。请严格依据下面的资料回答用户问题；"
                + "资料中没有的内容，请明确说明“资料中未找到”，不要编造。";
    }
}
```

### 6.4 两个设计点

1. **system 提示词每轮重建、不入历史库** —— 检索资料只服务当前问题，避免多轮对话中旧资料累计污染。
2. **消息按时间顺序排列**（system → 历史 → 当前问题），比原 `doChat` 的 `[当前问题, ...历史]` 更规范；原逻辑未改动。

### 6.5 验证结果

RagTest 端到端跑通：上传知识文档 → 提问「RAG 的具体流程是什么？」→ 模型回答以「**根据资料，RAG 的具体流程如下：**」开头，说明资料确实注入并生效。

## 七、强复用性设计要点

### 7.1 四个可替换维度

```text
解析   DocumentParser    → TikaDocumentParser（可换自研/OCR）
切分   DocumentSplitter  → ConfigurableDocumentSplitter（策略走配置）
存储   VectorStoreManager→ MilvusVectorStoreManager（可换 PGVector/ES 等）
管线   DocumentIngestor  → LangChain4jIngestor（复用项目 EmbeddingModel）
```

### 7.2 为什么这样写

- **接口抽象**：上层只依赖接口，底层实现替换不影响编排层与对外契约。
- **配置驱动**：切分策略、chunkSize、overlap、默认集合、向量维度全部走 properties。
- **集合参数化**：collectionName 贯穿入库/检索/删除/RAG，天然支持多知识库隔离。
- **复用既有 Bean**：`LangChain4jIngestor` 注入 `EmbeddingModel`、RAG 复用 `chatModel` + Redis 记忆，新能力零重复基建。
- **元数据贯穿**：documentId → chunk → 向量，支撑按文档删除、溯源、权限过滤。
- **零 DDL**：MilvusEmbeddingStore 首次写入自动建集合。

## 九、已知问题与排查（已修复）

### 9.1 运行时 NoSuchMethodError：UnsynchronizedByteArrayInputStream.builder() 【已修复】

现象：上传文档走到 Tika 解析时抛 `NoSuchMethodError`。
原因：easyexcel 带入 `commons-io 2.11`，Tika 3.0 需要 ≥2.16。
修复：provider pom 显式声明 `commons-io:2.16.1`。

### 9.2 运行时 NoClassDefFoundError：com.google.gson.ToNumberStrategy 【已修复】

现象：修复 9.1 后 Tika 解析继续报 `ClassNotFoundException`。
原因：kano-project-common 带入 `gson 2.8.6`，`ToNumberStrategy` 需要 ≥2.8.9。
修复：provider pom 显式声明 `gson:2.10.1`。

> 排查套路：`mvn dependency:tree -Dincludes=groupId:artifactId` 找到旧版本被谁带入，再在需要的模块显式声明直接依赖覆盖（直接依赖深度 1 优先于传递依赖）。

## 十、后续扩展建议

- **异步入库**：大文档用 `@Async` + 独立线程池，先返回 documentId，前端轮询状态，避免阻塞 Dubbo 线程。
- **RAG 引用溯源**：回答里带出「来自哪个文档第几段」，可在生成后让模型输出引用，或前端展示 `DocumentChunkVO`。
- **集合级权限**：metadata 带 userId/tenantId，检索时用 `Filter.and()` 叠加过滤。
- **增量更新**：上传前按 文件名+大小 hash 计算指纹，存在则先删旧文档再入库，实现幂等。
- **分块调优**：按文档类型选 recursive/paragraph，配合 chunkSize 控制召回粒度与 token 开销。
- **混合检索**：向量检索 + BM25 关键词检索融合，提升专业术语召回效果。
